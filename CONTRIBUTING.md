Contributions should normally be made via a pull-request against the project's
repository at https://github.com/damaki/community-bb-runtimes

For new runtime ports or complex/controversial contributions, please open
an issue first to gather feedback and discuss the design before starting work
that might be ultimately not accepted.

The guidelines below apply to everyone working on the code, people and coding
agents alike.

# Project Overview

This project generates GNAT runtimes for various bare-board targets. It works
by gathering various common and target-specific runtime source files and
combining them to produce runtimes for a target CPU. It is based on the runtime
generation infrastructure from https://github.com/adacore/bb-runtimes, with
some additional steps to turn the generated runtimes into configurable Alire
crates.

## Folder Structure

* `*_src/`: Contains target-specific runtime source files.
* `common_src/`: Contains source files that are shared across multiple targets.
* `tests/`: Contains the testsuite for performing various compilation and
  on-target sanity checks.
* `build-rts.py`: Generates a base runtime using the bb-runtimes infrastructure.
* `patch-runtime.py`: Adapts a runtime generated by `build-rts.py` to turn them
  into a configurable Alire crate.
* `generate-runtimes.sh`: Runs `build-rts.py` and `patch-runtime.py` to generate
  the final runtimes for all supported targets.

## Building and Testing

* Use `generate-runtimes.sh` to generate the runtimes. By default they are
  generated under the `install/` directory (you will need to delete the
  `install/` directory beforehand if it already exists).
* Runtimes can be compiled by running `alr build` from the runtime's directory
  (e.g. `install/light-tasking-rp2040/`)
* For testing, see [`tests/README.md`](tests/README.md).

## Coding Standards

Code should follow the [GNAT Coding Style](https://gcc.gnu.org/onlinedocs/gnat-style.pdf).

## LLM Policy

Users of LLMs must also read [LLM_POLICY.md](LLM_POLICY.md).

## New Runtime Guidelines

Before submitting a PR that adds a new runtime port, ensure that it:
* supports multiple (ideally all) microcontrollers within the same family
  (via crate configuration).
* uses Alire crate configuration variables to allow relevant parts of the
  runtime to be configured. The exact set of parameters that should be
  configurable vary depending on the runtime. Examples of configurable parameters
  are:
  * configuring the specific microcontroller used (e.g. STM32G474RE) within
    the chip family (e.g. STM32G4xx). This mainly affects the memory sizes used
    within the default linker scripts, but can also affect clock configuration
    in some cases.
  * clock configuration parameters;
  * interrupt stack sizes.
* passes all the tests on the target (see [tests/README.md](tests/README.md)).
  Note that it is not necessary to test on _every_ microcontroller in the
  family when there are only small differences in the runtime (e.g. different
  memory sizes).
* a relatively cheap (up to around 30 GBP) development board is available for
  the maintainers to purchase for use in pre-release testing and maintenance
  of the new runtime.

The intention is to:
* minimise the number of runtime crates by having one crate per chip family
  (plus runtime profile) instead of one crate per chip in the family;
* make it is easy to use the runtime crates; and
* make it is easy for users to adapt the runtime (via crate configuration) to
  suit their specific use case. For example, to adjust the main clock frequency.
